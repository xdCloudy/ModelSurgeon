# Chunk-streamed HF gradient memory and score comparison

## Question

Does backpropagating each calibration chunk before the next forward pass reduce measured CUDA peak allocation, and does fp16 accumulation order materially change the channel-removal scores used by the MLP gradient feature collector?

## Protocol

- Model: `Qwen/Qwen2.5-0.5B`, immutable Hugging Face revision `060db6499f32faf8b98477b0a26969ef7d8b9987`.
- Hardware: NVIDIA GeForce RTX 3060 12 GB; one CUDA device.
- Software: Python 3.14.7 environment, PyTorch `2.14.1+cu130`, Transformers from the local HF benchmark environment.
- Precision: fp16 model weights; logits are converted to fp32 for cross-entropy, as in the runtime.
- Calibration: 1,024 token budget, sequence length 128, 8 chunks, 1,016 causal targets. The text was a repeated synthetic sentence, SHA-256 `b056198b9e830ab226e1f7254d316c76b8d9d3a2ba83009b4733360323f7cc16`.
- Scope: gradients were enabled only for layer 0 MLP gate, up, and down projection matrices. Each mode ran three times in alternating order in one process. Peak allocated and reserved memory were read from CUDA allocator counters after synchronizing.
- Comparison: retained mode holds all chunk loss graphs until one backward call. Streamed mode backpropagates each summed chunk loss divided by the total target count before the next forward. Both use the same corpus-level token mean objective.
- Artifact: `tools/benchmark_gradient_graph_memory.py`; raw measurements are in `v1.8-gradient-graph-memory-evidence-v1.json`.
- Benchmark script SHA-256: `57518e50e9b6fd4666529bf2e95ca260ccc30d23ce00410af3921637e0bbfb95`.

## Results

| Metric | Retained graphs | Streamed backward |
| --- | ---: | ---: |
| Median incremental peak allocated | 1,917,462,528 B (1.786 GiB) | 504,612,864 B (0.470 GiB) |
| Median absolute peak allocated | 2,922,599,424 B | 1,509,749,760 B |
| Median peak reserved | 2,973,761,536 B | 1,570,766,848 B |
| Median elapsed time | 0.451 s | 0.432 s |

Streaming reduced incremental peak allocation by 1,412,849,664 B (about 1.316 GiB or 73.7%) for this workload. The near-identical runtime is a measurement on this small run only; it is not evidence of a general speedup.

FP16 gradient tensors were not elementwise `allclose` at `rtol=1e-4, atol=1e-6` (maximum absolute difference `6.10e-5`). This is consistent with changed floating-point accumulation order; relative error peaks are dominated by near-zero gradient entries. For the actual first-order channel-removal score `-sum(weight * gradient)` across the three projections, the maximum absolute difference was `2.12e-6` against a maximum score magnitude of `0.01404`; Spearman rank correlation was `0.99999994`. The lowest-score top 1% and top 5% channel sets were identical in all paired runs (minimum overlap 1.0).

## Interpretation and limits

This demonstrates a substantial reduction in measured autograd peak allocation for one small real HF checkpoint on the target consumer GPU, while preserving the candidate ranking for one layer and one synthetic calibration sample. It does not establish behavior across architectures, model scales, calibration corpora, or GPU memory pressure; it does not measure whole-model surgery, downstream quality, inference latency, or a statistically representative speed benefit. In particular, the strict elementwise gradient equality check fails in fp16, so further multi-seed and multi-model study is needed before making broader numerical-equivalence claims. Existing fp32 toy integration coverage remains useful but does not replace this study.

Reproduce with the model revision and calibration text used above, a CUDA-capable PyTorch environment, and:

```powershell
$env:PYTHONPATH = (Resolve-Path src).Path
python tools/benchmark_gradient_graph_memory.py `
  --model Qwen/Qwen2.5-0.5B `
  --revision 060db6499f32faf8b98477b0a26969ef7d8b9987 `
  --calibration-text <path-to-identical-calibration-text> `
  --sequence-length 128 --max-tokens 1024 --repeat 3 `
  --local-files-only --output gradient-memory-record.json
```

The text itself is intentionally not committed; matching its SHA-256 is necessary to reproduce this exact calibration run.
