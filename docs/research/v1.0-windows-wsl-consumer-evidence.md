This record closes the host-specific validation gap tracked by issue #200. It is
evidence for the documented Windows/WSL2 workflow, not a claim that every Windows,
WSL2, CUDA, or GGUF combination is supported.

## Validation commands and results

The Windows environment was installed from the locked project configuration:

```text
uv sync --extra dev --extra hf --locked
```

The focused contract suite passed on native Windows:

```text
uv run pytest tests/test_experiment_identity.py tests/test_artifact_store.py \
  tests/test_checkpoint_destination.py tests/test_gguf_disk.py \
  tests/test_gguf_resume.py tests/test_runtime_telemetry.py \
  tests/test_runtime_io_counters.py -q
```

Result: **35 passed**.

The same seven-file suite passed under Ubuntu 24.04/WSL2 in a clean temporary
Python 3.12 environment. The WSL environment installed the project with the
locked development dependencies before running the command. Result: **35 passed**.

The real Windows CUDA-offload smoke used the Apache-2.0 fixture and a bounded
single-turn generation:

```text
llama-cli.exe -m work/issue-200-validation/SmolLM2-135M-Q4_K_M.gguf \
  -ngl 99 -p ModelSurgeon_CUDA_smoke -n 8 --no-warmup -st --simple-io
```

The process exited successfully, loaded GGUF V3 metadata, selected `CUDA0
(NVIDIA GeForce RTX 3060)`, assigned layers 0 through 30 to `CUDA0`, and completed
an 8-token forward pass at 379.1 tokens/second. The verbose log recorded a CUDA
memory breakdown with 295 MiB self/model/context usage and a 20.4 MiB compute
buffer during the smoke.

The same native executable was invoked through WSL2 using forward-slash Windows
paths. WSL2 `nvidia-smi` reported the same RTX 3060 and driver, and the process
again exited successfully after an 8-token forward pass. Its verbose log recorded
`using device CUDA0`, layer assignment to CUDA0 for layers 0 through 30, and
370.9 tokens/second generation.

## Limitations and retained negative evidence

The host-specific smoke used the locally installed `llama.cpp` build
`de8656bd9`. It is not the revision-pinned compatibility runtime
`95b8e33e16bb9a60de780a70930ebf729db6a90a`; therefore this record does not expand
the repository's formal revision-pinned GGUF compatibility claims. The scheduled
compatibility workflow remains the authority for that matrix. A Linux-native
`llama.cpp` build was not claimed: the WSL2 CUDA check intentionally exercised the
Windows executable through WSL2, matching the installed host runtime. These are
explicit scope limits, not silently treated as equivalent evidence.
