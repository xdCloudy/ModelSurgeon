# FP32 gradient accumulation and full-model streaming evidence

This follow-up addresses low-precision gradient accumulation discrepancies found in the [BF16 comparison](v1.8-gradient-bfloat16-evidence.md), then measures chunk-streamed backward across every MLP layer of two Qwen2.5 checkpoints.

## Protocol

- Implementation: ModelSurgeon commit `d51f7f23abac9b1eca95e6782721e1901e84c160`.
- Models: `Qwen/Qwen2.5-0.5B` revision `060db6499f32faf8b98477b0a26969ef7d8b9987` and `Qwen/Qwen2.5-1.5B` revision `8faed761d45a263340a0528343f099c05c9a4323`.
- Calibration: the same 1,024-token window (eight 128-token chunks, 1,016 causal targets) from the `Salesforce/wikitext` `wikitext-2-raw-v1` training split. Input byte SHA-256: `dd19e768934268c03ddcf1e880debd6f862dbf23789a83e465f7aa3233ce4170`.
- Hardware/software: NVIDIA GeForce RTX 3060 12 GB, Python 3.14.7, PyTorch `2.14.1+cu130`, Transformers 5.10.1. Model weights use fp16 or bf16; cross-entropy logits are fp32. When supported, parameter gradient buffers are accumulated in fp32 without changing forward-weight precision.
- Comparison: retain all chunk graphs until backward versus backpropagate each chunk immediately. All MLP layers are measured for each full-model record. The 0.5B model has three paired allocator repeats; the larger 1.5B model has one paired repeat because of its higher memory use. Raw counters and numerical comparisons are in the linked JSON record.

The 1.5B run's highest reserved allocation was 11,525,947,392 bytes, below the RTX 3060's nominal 12 GB capacity. Streaming therefore reduced incremental peak allocation on this tested full model, while still using substantial GPU memory. Wall time varied between modes and this small sample does not establish a general speed improvement.

## Accumulation precision finding

The prior BF16 layer-only run used native low-precision accumulation. Its layer-0 top 5% set differed by one channel and the gradient and score vectors failed the strict allclose check. The updated collector requests fp32 gradient buffers where the installed PyTorch exposes the per-parameter `grad_dtype` facility, while leaving model forward precision unchanged. In the measured full-model runs, streamed and retained gradients and first-order scores passed `allclose(rtol=1e-4, atol=1e-6)`; selected top 1% and 5% sets matched. This makes the two collection paths numerically comparable in these measurements, not proof that the saliency scores predict physical pruning quality.

On PyTorch versions without per-parameter `grad_dtype`, the collector keeps the framework's native gradient accumulation behavior. That compatibility path does not receive the fp32 accumulation guarantee.

## Limits

These measurements establish GPU allocator behavior and equivalence between two gradient collection modes for one calibration window, two model sizes from one family, and one software/hardware setup. Only the 0.5B full-model case has three repeats; the 1.5B case is a single repeat. They do not measure pruning quality, downstream task retention, artifact size, inference latency, or generalize to other architectures, datasets, hardware, or PyTorch versions. Exact equality in a captured run is an observed result, not a cross-platform guarantee.
