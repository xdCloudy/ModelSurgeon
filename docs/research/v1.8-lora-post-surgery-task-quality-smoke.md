# Post-surgery LoRA task-quality pilot

## Result

The 128-step seed-42 run compared the pinned SmolLM2-135M source, a physically
pruned candidate, and the same candidate after held-out-selected LoRA repair.
All three artifacts were reloaded before evaluation. The existing local code
exact-match evaluator ran greedy generation with a 64-token limit on the same
four prompts for each arm.

| Arm | Code exact match | WikiText-2 mean test loss | Artifact bytes |
| --- | ---: | ---: | ---: |
| Source | 0/4 (0%) | 3.45508 | 272,437,465 |
| Pruned, no repair | 0/4 (0%) | 3.72457 | 265,801,794 |
| Pruned, LoRA selected | 0/4 (0%) | 3.42003 | 265,801,794 |

The four-example code score is at floor for the source model, so task-quality
retention is **inconclusive**. Equal zero scores do not show that pruning
preserved coding ability. This pilot demonstrates that task-quality evaluation
can run against the physical artifacts in the post-surgery study; it makes no
claim about downstream coding quality. The benchmark is intentionally reported
as four individual output digests in the JSON record, without treating the
sample as statistically meaningful.

The LoRA selector chose step 127 using the separate WikiText validation split.
On the shared 512-row WikiText test sample, its token loss was below the source
and substantially below the no-repair arm. The pruned artifact was 2.44% smaller
on disk than the source. These language-model measurements do not override the
inconclusive code result, and this run did not measure decode throughput.

## Limitation and next step

The source model is not validated as a coding-capable baseline on this tiny
benchmark. A larger, representative, properly licensed held-out coding set is
needed before this experiment can assess coding-quality retention. The default
LoRA study behavior remains unchanged unless `--task-quality-dataset` is given.
