# ModelSurgeon v1.0 release audit

This is the release-facing boundary for ModelSurgeon `v1.0.0`. It records the
claims that the repository can make, the evidence required to reproduce them,
and the limitations that must remain visible in release notes. A green build is
not permission to widen any claim below.

## Release identity

- Package and tag: `modelsurgeon==1.0.0` / `v1.0.0`
- Runtime: Python `>=3.12`
- Primary formats: Hugging Face `safetensors` checkpoints and native `GGUF`
- Source of truth for operation claims: the [architecture compatibility matrix](../architecture-compatibility.md)
- Source of truth for research claims: the [scientific results manifest](../research/v1.0-scientific-results.json)
- Archived reference inputs: [v1.0 reference manifests](v1.0-reference-manifests.json)

## Supported model and format boundary

| Model/profile | Release claim |
| --- | --- |
| Hugging Face dense Llama/SmolLM2 | Verified physical MLP, attention, layer, low-rank, and checkpoint operations with real save/reload evidence. |
| Hugging Face dense Qwen, Mistral, and Gemma | Analysis is verified; physical operations are experimental until a matching real-checkpoint proof exists. |
| Native GGUF F16 Llama, Qwen, Mistral, and Gemma | Analysis is verified; surgery cells remain experimental or unsupported according to the matrix. |
| Native GGUF Q4_K_M Llama | Verified physical MLP and checkpoint path, bounded by the pinned model and llama.cpp evidence. |
| Other GGUF family/profile combinations | Unknown or unsupported unless the matrix explicitly marks the cell otherwise. |

The supported user workflows are the [Hugging Face/safetensors guide](../user-guides/huggingface.md)
and the [native GGUF guide](../user-guides/native-gguf.md). A family name or a
successful toy fixture is not, by itself, a support claim.

## Codec boundary

The native registry contains exact block contracts for dense F32/F16/BF16,
Q2_K, Q3_K, Q4_K, Q5_K, Q6_K, and Q8_0 data. Q4_K_M and Q5_K_M are whole-file
recipes composed from their tensor codecs. End-to-end physical release evidence
is narrower: the pinned Q4_K_M Llama proof is the verified quantized surgery
claim; other codec/family combinations require their own matrix evidence.

## Acceptance evidence

- Main CI and CodeQL are green on the release predecessor commit; the release
  workflow repeats package build, metadata verification, clean Python 3.12
  installation, attestation, and approval-gated publication for `v1.0.0`.
- The pinned GGUF compatibility workflow covers structural operations, a CPU
  llama.cpp runtime, and the checked-in Llama, Mistral, Qwen, and Gemma fixtures.
- The consumer performance workflow is hardware-bound. Its reports are
  regression sentinels for the declared reference host, not universal hardware
  or model-quality benchmarks.
- The 18 v1.0 performance guardrails and the Windows/WSL2 consumer evidence are
  retained in the research manifest and must be read with their host-specific
  limitations.

## Limitations that ship with v1.0

- Research labels are mostly reversible single-channel mask outcomes on bounded
  calibration corpora; they do not establish task-general or deployment-general
  quality.
- Physical surgery, quantization error, latency, and evaluator results do not
  substitute for one another. A mask result does not prove a deployable rewrite.
- Hardware and runtime measurements are host-specific and must not be generalized
  across GPUs, drivers, operating systems, or native runtimes.
- Missing external models, datasets, or tools invalidate reproduction; they must
  be reported as unavailable rather than replaced with fabricated values.

## Publication gate

The GitHub `pypi` environment must have required reviewers and a configured PyPI
trusted publisher before a release is published. The release workflow must reach
the build and attestation jobs successfully, then pause at that environment gate
before uploading to PyPI. GitHub release attachments and attestations are not
evidence of a successful PyPI upload by themselves.
