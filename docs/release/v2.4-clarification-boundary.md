# ModelSurgeon v2.4 clarification release boundary

Status: the bounded v2.4 clarification boundary is verified by the
[machine-readable release record](../research/v2.4-clarification-release-v1.json).
This closes the clarification and ambiguity milestone as control-plane
infrastructure. It does not claim general natural-language understanding,
autonomous negotiation, or live provider/model-quality evidence.

## What is frozen

- Clarification is necessary-only. `ClarificationMachine` asks only for an
  executable hard constraint, required unresolved ambiguity, low-confidence
  required field, or explicit preference ordering. Executable, contradictory,
  unsupported, and refused policy outcomes do not receive a question.
- The policy is fail-closed with precedence `refused` → `unsupported` →
  `clarification_required` → `executable`. No answer can weaken, remove, or
  silently replace a hard constraint.
- Answers are typed records addressed to an existing deterministic question ID.
  An accepted answer creates a derived intent with explicit clarification
  provenance, then re-runs the canonical compiler and policy evaluator. Only
  that evaluator can expose an `OptimizationSpec`.
- Contradictory hard constraints remain refused. Conflicting soft preferences
  require an explicit selection among canonical field IDs; input order,
  confidence, provider output, and sentence wording cannot choose for the user.
- State, question, answer, transition, policy, provenance, study-result, and
  run identifiers are digest-derived from canonical JSON. Replay re-evaluates
  the root intent and answer sequence; altered state or policy is rejected.
- The boundary is side-effect free. Model inspection, capability checks,
  budgets, mutation, rollback, measurement, acceptance, publication, and source
  immutability remain deterministic ModelSurgeon responsibilities.

## Supported question policy and limitations

The following matrix is the v2.4 support boundary. “Supported” means that the
clarification layer can retain a typed field and ask a bounded question; it is
not a claim that the downstream optimizer can execute every cell.

| Cell | Status | Boundary behavior |
| --- | --- | --- |
| Typed hard constraint with metric, direction, threshold, and unit | Supported | Recompiled and policy-checked; no threshold is invented. |
| Typed soft objective with metric, direction, and unit | Supported | Preserved as a preference; no ordering is inferred. |
| Missing hard constraint or vague quality/latency/throughput/memory target | Supported clarification | One deterministic measurable question; no default threshold, baseline, or unit. |
| Deployment language (“serve”, “production”, “deploy”) | Supported clarification | Asks for a verified target and measurable runtime, memory, latency, or artifact-size budget; compatibility is not inferred. |
| Quality, latency, throughput, memory, disk size, parameter count, and perplexity labels | Supported target labels | The target assessor recognizes these labels; downstream contract support still governs execution. |
| Unknown or unverified metric | Unsupported | Retained as an explicit unsupported diagnostic; never coerced into a known metric. |
| Budget, allowed-operation, or deployment field absent from the v2 objective record | Unsupported downstream field | Retained and blocked by the v2.1 contract; it is not dropped or guessed. |
| Contradictory hard constraints | Refused | No question; the minimal conflict witness and all provenance remain visible. |
| Conflicting soft preferences | Supported clarification | The user must select one existing field ID; hard constraints remain unchanged. |
| Raw provider/free-text answer | Unsupported | Only bounded typed JSON answers are accepted at this boundary. |
| Arbitrary language, locale, or general conversation | Not claimed | Original text may be retained as provenance, but no general language understanding is promised. |
| Prompt-injection or instruction-like text in a typed fixture | Data only | It has no authority over policy, tools, objectives, or evidence. |

The target assessor’s recognized labels are intentionally narrower than a
general metric vocabulary. A “complete” target assessment means only that the
typed fields are complete and the policy is executable; it does not establish a
measured quality, deployment, or compatibility result.

## Evidence and known skips

The preregistered protocol `v24-clarification-measurement-v1` evaluates 11
typed fixture, held-out, and adversarial source cases against four policies,
retaining all 44 cells. The schema-driven policy met the shipping thresholds:
necessary-question recall 1.0, unnecessary-question rate 0.0,
silent-constraint-invention rate 0.0, executable precision/recall 1.0/1.0,
exact spec equivalence 1.0, and refusal correctness 1.0. The study is
control-plane evidence only; it is not a model-quality or provider benchmark.

The following remain explicit known skips or non-claims:

- no live provider replay seeds, hosted calls, credentials, or general-language
  benchmark were run;
- no autonomous objective negotiation or constraint amendment is implemented;
- no downstream execution, model inspection, mutation, artifact publication,
  deployment compatibility, or measured quality is established by this study;
- unsupported, refused, failed, low-confidence, and inconclusive cells remain
  retained and reproducible rather than being removed from the denominator;
- resource enforcement is bounded by the study limits (64 cases, 16 questions
  per case, and at most three provider replay seeds) and is not a claim of
  hostile-process containment.

## Reproduction and acceptance

From the repository root, run:

```text
python tools/run_clarification_study.py
python tools/run_clarification_study.py --json
python tools/audit_v24_clarification_release.py
```

The focused acceptance/replay checks are:

```text
python -m pytest -q tests/test_clarification.py tests/test_measurable_targets.py tests/test_clarification_study.py tests/test_v24_clarification_release.py
```

The JSON run ID and every result/question/state ID are deterministic. The
release audit rejects changed dependency identities, missing evidence paths,
support-matrix drift, live-evidence claims, missing limitations, and omitted
negative or inconclusive retention.
